# همیار — دانش‌یار امن سازمانی

نمونهٔ اولیهٔ فارسی برای پایگاه دانش سازمان همیاری شهرداری‌های خراسان رضوی. ورود با کد یک‌بارمصرف پیامکی، ورود اختیاری Google OAuth، تأیید مدیر برای حساب‌های تازه، نقش‌های دسترسی، جداسازی اسناد بر اساس شهرداری، ثبت رویدادهای امنیتی و رمزنگاری داده‌های ذخیره‌شده در پیکربندی production در نظر گرفته شده است. این پروژه هنوز پیش‌نیازهای استقرار رسمی سازمان را کامل نمی‌کند؛ بخش «محدودیت‌ها» را پیش از استفاده از دادهٔ واقعی بخوانید.

## اجرای محلی و پیش‌نمایش توسعه

نیازمندی: Node.js 18 یا بالاتر؛ وابستگی npm ندارد.

```bash
npm start
```

سپس `http://localhost:8000` را باز کنید. برای تغییر پورت: `PORT=8080 npm start`. راهنمای گام‌به‌گام ویندوز/XAMPP در [راهنمای راه‌اندازی](راهنمای-راه‌اندازی-ویندوز-XAMPP.md) و اجرای یک‌کلیکی دمو در `start-local-demo.bat` است.

برای آزمایش ورود در رایانهٔ توسعه، OTP نمایشی را فعال کنید:

```bash
AUTH_DEV_MODE=true ALLOW_FIRST_ADMIN=true DEV_AUTO_APPROVE_USERS=true npm start
```

این حالت کد آزمایشی را در رابط و لاگ سرور نشان می‌دهد، اولین حساب را مدیر می‌کند و با `DEV_AUTO_APPROVE_USERS=true` حساب‌های نمایشی جدید را خودکار فعال می‌کند (حتی pendingهای قبلی دمو را هنگام اجرا فعال می‌کند). این رفتار فقط برای رفع اصطکاک آزمایش است؛ در محیط واقعی حساب‌های تازه باید با تأیید مدیر فعال شوند. برای **پیش‌نمایش توکار** که مرورگر third-party cookie را مسدود می‌کند، `AUTH_PREVIEW_BEARER=true` نیز نشست آزمایشی را فقط در sessionStorage همان تب نگه می‌دارد. این توکن فقط همراه حالت توسعه صادر/پذیرفته می‌شود. **هرگز `AUTH_DEV_MODE`، `AUTH_PREVIEW_BEARER` یا `DEV_AUTO_APPROVE_USERS` را در production فعال نکنید**؛ برنامه در صورت ترکیب حالت توسعه/خودتأییدی با `NODE_ENV=production` از اجرا خودداری می‌کند. در محیط واقعی کد فقط از مسیر درگاه پیامک ارسال می‌شود.

## تنظیم ورود و راه‌اندازی عملیاتی

فایل `.env.example` نام تنظیمات را نشان می‌دهد؛ Node.js آن را خودکار بارگذاری نمی‌کند. مقادیر واقعی را از طریق مدیر اسرار سازمان، محیط سرویس systemd یا orchestrator تزریق کنید. اسرار واقعی را در Git یا چت قرار ندهید.

### پیامک و حساب کاربری

- `SMS_GATEWAY_URL` و `SMS_GATEWAY_TOKEN`: آداپتور پیامک سازمان باید endpoint HTTPS داشته باشد، درخواست `POST` با هدر `Authorization: Bearer ...` و بدنهٔ `{"to":"+989...","message":"..."}` را بپذیرد و در موفقیت HTTP 2xx برگرداند. اگر شرکت پیامکی سازمان قرارداد متفاوتی دارد، آداپتور سمت سرور را با API همان شرکت تطبیق دهید.
- کاربر شمارهٔ خود را با کد کشور تأیید می‌کند؛ حساب‌های عادی تا تأیید مدیر در وضعیت انتظار می‌مانند.
- `ADMIN_BOOTSTRAP_PHONE`: شمارهٔ تأییدشدهٔ مدیر اولیه را مشخص کنید. آن شماره پس از OTP مدیر می‌شود. پس از ساخت و بررسی مدیر اولیه، این مقدار را از محیط سرویس حذف کنید.
- نقش‌های سامانه: مدیر سامانه، مدیر دانش و کاربر شهرداری. مدیر سامانه عضویت و نقش‌ها را مدیریت می‌کند. مدیر دانش فایل بارگذاری می‌کند؛ می‌تواند فایل را فقط برای شهرداری خودش منتشر کند. انتشار عمومی و مدیریت سراسری در اختیار مدیر سامانه است.
- کاربران فعال فقط اسناد سازمانی و اسناد متعلق به شهرداری خود را می‌بینند؛ کاربران عادی نمی‌توانند سند بارگذاری یا حذف کنند.

### ورود Google

برای فعال‌سازی، در Google Cloud یک OAuth Client از نوع Web بسازید و `GOOGLE_CLIENT_ID`، `GOOGLE_CLIENT_SECRET` و `GOOGLE_REDIRECT_URI` را تنظیم کنید. نشانی callback باید دقیقاً `https://دامنه-سازمان/auth/google/callback` باشد و همان نشانی در کنسول Google ثبت شود. ابتدا هویت گوگل بررسی می‌شود و سپس کاربر باید شمارهٔ همراه را با OTP تأیید کند؛ اتصال ایمیل به شماره بدون تأیید هر دو انجام نمی‌شود. چون OAuth گوگل سرویس خارجی است، این مسیر به دسترسی خروجی اینترنت نیاز دارد؛ هستهٔ جست‌وجو و پاسخ‌گویی می‌تواند داخلی/آفلاین بماند.

### HTTPS، کلیدها و داده

- `NODE_ENV=production`، `PUBLIC_URL=https://دامنه-سازمان`، `DATA_ENCRYPTION_KEY` و پیکربندی HTTPS پیامک و مدیر اولیه برای شروع production الزامی است. برنامه بدون این مقادیر اجرا نمی‌شود.
- کلید رمزنگاری دقیقاً ۳۲ بایت (۶۴ رقم hex یا base64 معادل) باشد؛ نمونهٔ تولید: `openssl rand -hex 32`. این کلید را خارج از پوشهٔ پروژه و با دسترسی محدود نگهداری کنید. اسناد، حساب‌ها، نشست‌ها، بازخوردها و audit در فایل‌های JSON با AES-256-GCM رمز می‌شوند. گم‌شدن کلید یعنی ناتوانی در خواندن داده؛ فرایند پشتیبان‌گیری و چرخش کلید باید قبل از استقرار طراحی و آزمایش شود.
- فایل‌های داخل `data/` محلی و در Git نادیده گرفته شده‌اند. مجوز پوشه در production محدود می‌شود. پیش‌نمایش توسعه کلید رمزنگاری ندارد و داده‌هایش **برای محرمانه‌ماندن طراحی نشده‌اند**.
- برنامه را فقط پشت reverse proxy مورداعتماد با TLS و محدودسازی دسترسی شبکهٔ سازمان منتشر کنید؛ پورت Node را مستقیماً به اینترنت باز نکنید. پراکسی باید هدر `X-Forwarded-Proto: https` را خودش تنظیم کند. `TRUST_PROXY=true` را فقط وقتی فعال کنید که پراکسی ورودی `X-Forwarded-For` را پاک و از نو مقداردهی می‌کند.

## مدل محلی و استفادهٔ آفلاین

بدون مدل، جست‌وجوی محلی روی اسناد کار می‌کند و گزیدهٔ منبع را نشان می‌دهد. برای پاسخ‌سازی زبانی Ollama را روی همان سرور یا شبکهٔ داخلی نصب کنید:

```bash
ollama pull qwen2.5:7b
OLLAMA_MODEL=qwen2.5:7b npm start
```

مرورگر مستقیماً به Ollama وصل نمی‌شود. دریافت مدل اولیه معمولاً اینترنت می‌خواهد؛ پس از انتقال مدل و ابزارهای لازم، اجرای پاسخ‌سازی می‌تواند داخل شبکه و بدون وب باشد. ورود Google برخلاف هستهٔ سامانه آفلاین نیست؛ در شبکهٔ کاملاً ایزوله آن را غیرفعال و از درگاه پیامک داخلی/سازمانی استفاده کنید.

## محتوای نمونهٔ کتابخانه

در اولین اجرا سه یادداشت عمومی دربارهٔ معرفی سازمان، حوزه‌های فعالیت اعلام‌شده و استانداری/استان اضافه می‌شود. منابع و تاریخ گردآوری داخل فایل‌ها هستند. این یادداشت‌ها بخشنامه یا سند حقوقی نیستند. آمار قدیمی به‌عنوان آمار جاری بازنشر نشده است.

فرمت‌های متنی فعلی: TXT، MD، CSV، JSON، LOG و HTML. PDF و Word هنوز استخراج نمی‌شوند. اصلاح پاسخ کاربران به‌عنوان راهنمای مدل محلی ذخیره می‌شود، اما وزن‌های مدل خودکار آموزش نمی‌بینند و بازخورد جای سند مصوب را نمی‌گیرد.

## کنترل‌های امنیتی موجود

OTP شش‌رقمی با انقضای پنج‌دقیقه‌ای، محدودیت تلاش و درخواست، نشست تصادفی هشت‌ساعته در کوکی HttpOnly/SameSite (در صورت اجرا داخل iframe، امکان تنظیم `SameSite=None; Secure; Partitioned`)، CSRF token برای عملیات تغییردهنده، PKCE/state/nonce و بررسی امضای Google ID token، هدرهای CSP و ضد iframe، کنترل مجوز سمت سرور، ثبت رویدادهای مهم و رمزنگاری AES-GCM فایل‌های داده در production.

## محدودیت‌ها — پیش از اسناد واقعی لازم است

این نسخه **گذراندن ارزیابی امنیتی سازمان یا آمادهٔ استقرار حساس را ادعا نمی‌کند**. ذخیره‌سازی فعلی فایل‌محور است؛ محدودکنندهٔ OTP در حافظهٔ یک فرایند است و برای چند نمونهٔ هم‌زمان، خوشهٔ سرور یا مقابلهٔ سازمانی با حمله باید به Redis/WAF/سامانهٔ احراز هویت مصوب مهاجرت کند. سامانه هنوز آزمون نفوذ، پشتیبان‌گیری و بازیابی رمز‌شده، نگهداری امن کلید در KMS، پایش هشدار، retention/حذف داده، بازیابی مدیر، مدیریت چرخهٔ عمر نشست، اسکن بدافزار فایل، تبدیل PDF/Word، مدیریت محرمانگی/طبقه‌بندی اسناد یا ثبت ممیزی تغییرناپذیر ندارد. احراز هویت و مجوزهای فعلی پایهٔ اجرایی هستند و باید با سیاست امنیت اطلاعات، واحد حقوقی و تیم زیرساخت سازمان بازبینی شوند.

پیش از بهره‌برداری: آداپتور پیامک را با ارائه‌دهندهٔ واقعی یکپارچه کنید؛ OAuth گوگل را با دامنهٔ نهایی آزمایش کنید؛ TLS، فایروال، پشتیبان‌گیری، چرخش کلید، آستانهٔ rate-limit و هشدارها را راه‌اندازی کنید؛ فهرست شهرداری‌ها و هویت سازمانی کاربران را از مرجع معتبر تأیید کنید؛ و با دادهٔ آزمایشی آزمون دسترسی بین شهرداری‌ها و آزمون نفوذ انجام دهید. مدل زبانی می‌تواند اشتباه کند؛ پاسخ‌ها باید همراه سند معتبر بازبینی شوند.
